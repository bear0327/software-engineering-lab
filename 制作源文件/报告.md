## 1 项目说明

本实验继续设计实验一的酒店预订系统，主要完成模块划分、UML建模、数据存储设计和界面设计。本次只做设计与原型，业务后端及相关测试留在后续实验完成。

设计依据是实验一的 requirements.md，共26条需求。实验一基线中22条已确认，包括18条功能需求、3条非功能需求和1条约束；其余4条涉及的处理细节在本次设计中补充为明确规则，见4.4节。实验一原始记录保留不变。

系统有顾客、酒店工作人员和平台管理员三类用户。游客可以浏览公开信息；顾客登录后管理自己的订单；工作人员只处理所属酒店的业务；管理员负责酒店审核启停、工作人员账号、异常订单及平台统计日志。管理员处理异常也要遵守订单状态规则并记录原因。

主要功能包括：账号认证和权限隔离、酒店及房型资料、每日供给与价格及停售、城市/日期/人数/房型/价格组合查询、提交预订、酒店确认或拒绝、待确认修改、取消、现场入住与正常退房、自动超时与未入住处理、临时停业处置、有效预订和间夜统计、关键操作审计。

本项目不包括在线支付、退款、评价、优惠券、地图、会员积分、第三方渠道接口、具体房间分配、清洁维修、提前入住、延迟退房和续住，住宿费用由酒店线下结算。通知暂按平台待办和线下联系记录设计。

## 2 软件结构与模块划分

系统采用分层单体结构，分为展示层、应用层、领域层和持久化层。业务模块部署在同一个应用中，使用同一个数据库。这样，创建订单和更新多日库存可以放在一次事务中，不必另外处理跨服务事务。界面通过应用服务操作数据，不直接修改库存或订单状态。

| 模块 | 主要职责与交互 | 需求来源 |
| --- | --- | --- |
| M01 认证与权限 | 登录注册、账号启停、角色与本人/本酒店范围校验；所有写入口共同使用 | REQ-001、023 |
| M02 酒店与房型 | 酒店审核启停、房型资料、每日价量及停售；向查询和预订提供可售前提 | REQ-002、003 |
| M03 查询与报价 | 组合查询、全程可订判断、逐夜报价与总价；下单时再次核对价格和库存 | REQ-004、007 |
| M04 预订生命周期 | 建单、确认拒绝、修改取消、入住退房、版本及请求去重；编排库存事务 | REQ-005—016、020 |
| M05 库存与价格 | 房型日历、预留净变化、原子释放、价格快照校验；不自行改变订单状态 | REQ-003、006、007、011 |
| M06 异常与调度 | 超时、未入住、停业逐单处置；统一调用生命周期服务，不另写一套状态逻辑 | REQ-010、015、017 |
| M07 统计与审计 | 有效预订/间夜、授权范围查询、只读操作历史和日志 | REQ-018、019 |
| M08 持久化与恢复 | 关联约束、索引、事务、备份和通知待办 | REQ-020、024 |

权限和状态条件由策略类检查，事务由应用服务组织，数据读写由Repository完成。这样的划分可以让不同页面共用同一套库存规则。统计只读取业务数据，不参与订单和库存的写入。

## 3 类与数据设计

Booking表示订单，BookingNight保存各住宿夜的价格和占用情况，RoomDay记录房型每天的供给、已占用数量和价格。BookingService组织订单处理事务，InventoryService计算库存变化；AuthorizationPolicy检查身份和数据归属，TransitionPolicy检查状态及时限。

三类用户统一保存在用户表中，通过role区分；工作人员还需绑定唯一的hotelId。订单关联顾客、酒店和房型，订单酒店必须与房型所属酒店一致。逐夜成交价单独保存在BookingNight中，避免酒店调价后影响已经生成的订单。

| 数据表 / 对象 | 关键字段、约束与索引 |
| --- | --- |
| app_user | id主键、账号唯一、password_hash、role、hotel_id、enabled；工作人员必须绑定且仅绑定一个有效酒店 |
| hotel | id主键、名称城市地址联系方式、审核/营业状态、IANA时区字段time_zone；示例为Asia/Shanghai；city/status组合索引 |
| room_type | id主键、hotel_id外键、名称、capacity>0、total_rooms>0；hotel_id索引 |
| room_day | 联合主键(room_type_id,stay_date)；supply、reserved、price、sold_out、version；CHECK 0≤reserved≤supply；供给不超过房型总数由同事务校验 |
| booking | id主键、customer/hotel/room_type外键、日期、间数人数、联系人、状态、总价、版本、pending_since/expires_at；check_out>check_in；数量>0 |
| booking_night | 联合主键(booking_id,stay_date)；对应房型日历、成交单价、间数、占用标记；一订单同住宿日不重复 |
| request_record | UNIQUE(actor_id,operation,request_key)；内容哈希、完成结果码、结果对象；服务端重试不新增业务效果 |
| audit_log / notification_task | 审计含操作者、对象、酒店、动作、前后状态、结果原因和时间；通知待办保存关联订单、状态与重试次数 |

订单表计划建立(customer_id,created_at)、(hotel_id,status,check_in)、(status,expires_at)索引；审计表建立(hotel_id,occurred_at)、(actor_id,occurred_at)索引。查询结果分页返回，索引效果在后续性能测试中验证。

取消、停业和账号停用均保留历史引用，不级联删除订单。订单修改后保留当前有效逐夜明细，旧日期、价格和联系人变更写入审计。审计只保存脱敏电话，不保存完整电话号码、密码或整份请求。日志保留180天，到期由独立的系统清理任务删除；管理员和酒店人员均无手动改写、删除入口。

## 4 主要业务处理

### 4.1 跨日库存与价格

住宿区间为 [入住日,离店日)。例如11月10日入住、12日离店，只占10日和11日的库存；预订两间房，则两晚各占两间。某日剩余房量等于供给总量减去仍应占用的房量，供给总量和剩余房量需要分开记录。

订单创建成功立即预留全部住宿夜，进入待确认；确认与入住不再次扣减。任一夜无房、停售、缺失日历或发生写入失败，整单回滚，不拆单、不留下半段预留。查询页面只作可订提示，提交时必须重查当前日历。

总价=所有住宿夜成交单价之和×房间数。示例：299元与359元两晚、一间，共658元。提交携带用户已接受的报价版本；锁后价格变化则返回新逐夜价并要求重新确认，不静默按新价成交。订单生成后保留逐夜快照，酒店后续调价不改变旧单。

### 4.2 事务边界、锁定与幂等

一次建单事务包含：认领请求键、核验酒店营业及房型状态、锁定全程日历、复查价格与库存、写逐夜预留、创建订单与成交快照、保存请求结果、成功审计和通知待办。所有写入共用一个 UnitOfWork，任一步失败整体回滚。失败安全审计在回滚后独立记录，避免失败日志也被业务事务撤销。

身份校验及已有请求结果读取可以在事务前进行，但请求键的唯一认领必须在事务中使用唯一约束完成。并发同键冲突等待首个请求提交后再读取结果；如果首请求回滚则允许安全重试。业务已提交但响应断网时，原键返回原结果，而不是新建第二笔订单。

为避免最后一间竞争，所有库存相关操作按(roomTypeId,stayDate)固定顺序锁定受影响日历并重读，满足 reserved+delta≤supply 后才更新。创建使用酒店/房型共享锁，停业和房型维护使用冲突锁，确保“营业检查通过后恰好停业”不会穿透。改单先锁该订单，再锁酒店及排序后的房型、日历；停业操作只改变酒店状态，逐单取消另开事务，不能持有酒店锁后反向遍历并锁所有订单。

请求键以“操作者+操作类型+唯一键”区分。不同请求键允许顾客主动创建同日期多笔订单；同键、同内容重发返回原处理结果。同键但内容不同则返回409和REQUEST_KEY_CONFLICT，不修改原请求结果，也不执行新操作；顾客重新发起不同预订时使用新请求键。正常无房等已完成业务拒绝可以保存稳定结果，瞬时服务器故障允许原键安全重试。

订单版本用于阻止旧页面覆盖新状态。请求携带 expectedVersion；锁后版本或状态变化时返回409与最新版本，界面要求刷新。授权校验必须在服务端执行，不能只隐藏按钮。确认先成功后，取消在刷新后仍可按截止规则成功；取消先成功则确认必须拒绝，这不是简单的“二者永远只有一个能成功”。

### 4.3 修改、取消和库存释放

处于“待确认”状态（即顾客已提交、酒店尚未确认）的订单，可以修改日期、房型、间数和联系人。修改时锁定新旧日期所涉及的全部库存记录，逐日计算库存变化量，即新占用量减去原占用量。同一房型的重叠日期如果变化量为零，就保留原有占用，不重复扣减。示例：原10日和11日各占一间，缩短为只住10日，10日不动、11日释放一间；扩展到无房的12日则整体失败，原价格和预留不变。保存修改前需让顾客确认新价格；修改成功后，从本次成功修改时重新计算30分钟的酒店确认时限。

已确认只允许修改联系人，不回到待确认、不重开计时。日期、房型或间数变化按允许条件取消后重新下单。改单只限原酒店，跨酒店住宿需取消后重新预订。

顾客可取消待确认订单；已确认且未入住，只允许在入住日酒店当地18:00前取消，18:00整及以后拒绝。取消或拒绝只释放仍应归还的未消费预留；重复请求按原结果返回，库存不会再次增加。正常退房不回补已消费的历史夜。

未入住在酒店当地入住日次日00:00判定：一晚订单没有未来夜可返还；三晚订单只归还后两晚。BookingNight采用HELD/CONSUMED/RELEASED标记区分历史消费与已释放记录；RoomDay.reserved保留历史未返还占用，不把历史夜重新出售。时区换算按4.4节的统一规则处理。

### 4.4 停业、超时及补充规则

临时停业先禁止新订，再由管理员逐笔处置待确认及已确认订单，原因必填，取消与释放同事务；通知生成可查询的待办，失败可重试。已入住订单维持当前状态，转人工协调；恢复营业必须管理员主动启用。房型单纯停售原则上履行原订单，不能由此推出原单可无限扩大占用。

以下规则作为实验二的设计约定，用于实现和编写测试用例。

| 编号 | 处理事项 | 采用的规则 |
| --- | --- | --- |
| P01 / REQ-010 | 确认时限与后台任务延迟 | 采用严格截止。锁定订单后读取服务器当前时间，达到expiresAt即不能确认或修改；即使后台任务未执行，也先将订单置为已超时并释放一次库存，再返回超时提示。到期前的合法确认成功后不再超时 |
| P02 / REQ-017 | 停售期间修改原订单 | 联系人可以修改。库存修改逐日比较新旧占用：停售日期不允许增加占用，允许减少间数、缩短区间或移出该日；其他日期须可售且有足够库存。任一条件不满足，原单不变。酒店停业后禁止日期、房型及间数修改，仍可按规则取消 |
| P03 / REQ-021、022 | 性能测试基线 | 统一硬件、软件、数据及请求组合，使用第6节列出的环境。查询和预订各20并发、100次，分别按2秒和3秒门槛判断，失败和超时不剔除 |
| P04 / 其他边界 | 日期、时区、请求与计时 | 使用下列统一约定，不再在页面和接口中各自解释 |

订单创建或成功修改时记录expiresAt，值为本次计时起点加30分钟。确认操作以持有订单锁时核验的服务器时间为准，当前时间必须早于expiresAt，恰好到期也拒绝。后台任务每5秒扫描一次到期订单；写接口同时做超时检查，避免任务延迟扩大确认期限。并发确认、修改、取消和超时处理均校验最新状态，库存只释放一次。

每家酒店保存IANA时区名称，如Asia/Shanghai。入住、离店使用酒店当地日期；创建时间、截止时刻和日志时间统一保存为UTC时间戳，页面显示时再换算。取消截止为酒店当地入住日18:00，未入住判定为当地次日00:00。

未填写入住及离店日期时，只浏览酒店和房型基本资料，不显示全程总价或可订结论，价格范围筛选暂不可用。只填写一个日期时提示补齐日期，不进行住宿区间查询。

统计区间包含开始日和结束日，按计划入住日期决定是否纳入。例如选择11月1日至11月30日，两个端点当天入住的有效订单都计入；跨区间住宿不按每一晚拆分。有效状态仍仅为已确认、已入住、已退房。

易用性测试中，5名首次用户分别在桌面和手机完成一次查询及预订，每端单独计时。从开始填写查询条件到看到预订成功结果为止，错误提示阅读和重试均计入时间，不由测试人员代操作；至少4人在两端均能于4分钟内独立完成。记录设备、浏览器版本和实际用时。

## 9 实验小结

酒店预订的主要难点是多日库存和订单状态保持一致。每日供给与剩余量要分开，改单时要考虑原有预留，重复取消不能再次释放库存；未入住和正常退房也不能按同一种方式归还房量。

本次将这些处理集中到BookingService、库存服务和状态策略中，页面及定时任务共用同一套规则。超时按严格截止处理，停售时逐日核对是否增加占用，日期与测试条件也统一规定，后续按这些规则实现和验证。

报告后附全部UML和界面图。提交目录中另保存原尺寸图片和PlantUML源文件，便于查看和修改。
