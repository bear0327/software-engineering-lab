## 1 项目概况与设计依据

本实验延续 LAB1 的酒店预订系统。设计目标是将需求转换为可追踪的模块、领域对象、交互流程、存储约束和 UI 原型，为后续实现与测试提供依据。本次不实现真实业务后端，不宣称已通过并发、性能、安全或备份恢复测试。

设计依据为当前工作区 LAB1 提交目录内的 requirements.md。共26条需求：功能20条、非功能5条、约束1条；其中22条已确认（功能18、非功能3、约束1），另4条待确认。LAB1 的内容及固定标签保持不变，本实验另建本地 Git 仓库。

系统服务顾客、酒店工作人员和平台管理员。游客可以浏览公开信息，登录顾客只管理本人订单；工作人员只处理绑定酒店的业务；管理员负责酒店审核启停、工作人员账号、异常订单及平台统计日志。不把管理员设计成可随意修改订单状态的超级业务账号。

主要功能包括：账号认证和权限隔离、酒店及房型资料、每日供给与价格及停售、城市/日期/人数/房型/价格组合查询、提交预订、酒店确认或拒绝、待确认修改、取消、现场入住与正常退房、自动超时与未入住处理、临时停业处置、有效预订和间夜统计、关键操作审计。

明确不实现在线支付、退款、评价、优惠券、地图、会员积分、第三方渠道接口、具体房间分配、清洁维修、提前入住、延迟退房和续住；住宿费用线下结算。原型中的通知是平台待办与线下联系记录，不表示接入短信供应商。

## 2 总体架构与模块划分

采用“展示层—应用层—领域层—持久化层”的分层单体。一个应用部署单元共享一个事务数据库，避免在课程规模下引入微服务、分布式事务与复杂消息基础设施。模块之间通过应用服务协作；界面不能直接写库存或覆盖订单状态。

| 模块 | 主要职责与交互 | 需求来源 |
| --- | --- | --- |
| M01 认证与权限 | 登录注册、账号启停、角色与本人/本酒店范围校验；所有写入口共同使用 | REQ-001、023 |
| M02 酒店与房型 | 酒店审核启停、房型资料、每日价量及停售；向查询和预订提供可售前提 | REQ-002、003 |
| M03 查询与报价 | 组合查询、全程可订判断、逐夜报价与总价；返回报价版本，不承诺查询结果等于下单成功 | REQ-004、007 |
| M04 预订生命周期 | 建单、确认拒绝、修改取消、入住退房、版本及请求去重；编排库存事务 | REQ-005—016、020 |
| M05 库存与价格 | 房型日历、预留净变化、原子释放、价格快照校验；不自行改变订单状态 | REQ-003、006、007、011 |

分层理由：将“是否允许操作”“如何组织一次事务”“怎样存储”分别放入策略、应用服务和 Repository。后续可以替换数据库或展示页面，而无需在每个页面重写库存规则。统计使用只读投影查询，但订单与库存写入不依赖最终一致性的异步补偿。

## 3 面向对象设计与数据存储

领域对象 Booking 聚合一次订单及逐夜快照 BookingNight，负责状态合法性；RoomDay 表达某房型某住宿夜的供给和占用。InventoryService 处理跨聚合的净变化，BookingService 统一事务编排。AuthorizationPolicy 与 TransitionPolicy 分别隔离身份归属和状态时限规则。Repository 提供锁定和保存能力，不私自决定业务是否允许。

类图使用关联与基数表达归属，不为三类用户机械建立三个重复用户表；User.role 与可选 hotelId 表达角色和工作人员的唯一酒店绑定。订单关联顾客、酒店和房型；RoomType.hotelId 必须与 Booking.hotelId 一致。逐夜成交价保留在 BookingNight，不依赖后来变化的 RoomDay.price。

| 数据表 / 对象 | 关键字段、约束与索引 |
| --- | --- |
| app_user | id主键、账号唯一、password_hash、role、hotel_id、enabled；工作人员必须绑定且仅绑定一个有效酒店 |
| hotel | id主键、名称城市地址联系方式、审核/营业状态、可选IANA时区技术字段；city/status组合索引 |
| room_type | id主键、hotel_id外键、名称、capacity>0、total_rooms>0；hotel_id索引 |
| room_day | 联合主键(room_type_id,stay_date)；supply、reserved、price、sold_out、version；CHECK 0≤reserved≤supply；供给不超过房型总数由同事务校验 |
| booking | id主键、customer/hotel/room_type外键、日期、间数人数、联系人、状态、总价、版本、pending_since/expires_at；check_out>check_in；数量>0 |
| booking_night | 联合主键(booking_id,stay_date)；对应房型日历、成交单价、间数、占用标记；一订单同住宿日不重复 |
| request_record | UNIQUE(actor_id,operation,request_key)；内容哈希、完成结果码、结果对象；服务端重试不新增业务效果 |
| audit_log / notification_task | 审计含操作者、对象、酒店、动作、前后状态、结果原因和时间；通知待办保存关联订单、状态与重试次数 |

订单建议建立(customer_id,created_at)、(hotel_id,status,check_in)、(status,expires_at)索引；审计建立(hotel_id,occurred_at)、(actor_id,occurred_at)索引。范围查询与分页避免一次传输所有记录。索引是设计建议，不是性能已达标的证据。

取消、停业和账号停用均保留历史引用，不级联删除订单。订单修改成功后保留当前有效逐夜明细，将旧日期、价格和联系人变更快照记入受控审计；日志界面脱敏，原始敏感字段保留范围仍待确认，不将整份请求和明文密码写入日志。

## 4 业务规则、事务与异常设计

### 4.1 跨日库存与价格

住宿区间为左闭右开 [入住日,离店日)。11月10日入住、12日离店只占10日和11日；两间房则这两晚各占两间。某日剩余=供给总量−仍应占用的房量，绝不能把“剩余”再当作“总量”减一遍占用。

订单创建成功立即预留全部住宿夜，进入待确认；确认与入住不再次扣减。任一夜无房、停售、缺失日历或发生写入失败，整单回滚，不拆单、不留下半段预留。查询页面只作可订提示，提交时必须重查当前日历。

总价=所有住宿夜成交单价之和×房间数。示例：299元与359元两晚、一间，共658元。提交携带用户已接受的报价版本；锁后价格变化则返回新逐夜价并要求重新确认，不静默按新价成交。订单生成后保留逐夜快照，酒店后续调价不改变旧单。

### 4.2 事务边界、锁定与幂等

一次建单事务包含：认领请求键、核验酒店营业及房型状态、锁定全程日历、复查价格与库存、写逐夜预留、创建订单与成交快照、保存请求结果、成功审计和通知待办。所有写入共用一个 UnitOfWork，任一步失败整体回滚。失败安全审计在回滚后独立记录，避免失败日志也被业务事务撤销。

身份校验及已有请求结果读取可以在事务前进行，但请求键的唯一认领必须在事务中使用唯一约束完成。并发同键冲突等待首个请求提交后再读取结果；如果首请求回滚则允许安全重试。业务已提交但响应断网时，原键返回原结果，而不是新建第二笔订单。

为避免最后一间竞争，所有库存相关操作按(roomTypeId,stayDate)固定顺序锁定受影响日历并重读，满足 reserved+delta≤supply 后才更新。创建使用酒店/房型共享锁，停业和房型维护使用冲突锁，确保“营业检查通过后恰好停业”不会穿透。改单先锁该订单，再锁酒店及排序后的房型、日历；停业操作只改变酒店状态，逐单取消另开事务，不能持有酒店锁后反向遍历并锁所有订单。

请求键以“操作者+操作类型+唯一键”区分。不同请求键允许顾客主动创建同日期多笔订单；同键重发只产生一次业务效果。对同键不同内容，候选方案为拒绝并返回 REQUEST_KEY_CONFLICT，尚未获得业务确认，不标记为新确认规则。正常无房等已完成业务拒绝可以保存稳定结果，瞬时服务器故障不伪装为已完成请求。

订单版本用于阻止旧页面覆盖新状态。请求携带 expectedVersion；锁后版本或状态变化时返回409与最新版本，界面要求刷新。授权校验必须在服务端执行，不能只隐藏按钮。确认先成功后，取消在刷新后仍可按截止规则成功；取消先成功则确认必须拒绝，这不是简单的“二者永远只有一个能成功”。

### 4.3 修改、取消和库存释放

待确认可改日期、房型、间数和联系人。修改时锁定旧新日历键的并集，对每键计算 delta=新占用−原占用；同房型重叠夜 delta=0 时保留一次占用。示例：原10日/11日各一间，缩短为只住10日，10日不动、11日释放一间；扩展到无房的12日则整体失败，原价格和预留不变。成功后重核价并重置30分钟确认计时。

已确认只允许修改联系人，不回到待确认、不重开计时。日期、房型或间数变化按允许条件取消后重新下单。跨酒店修改不在已确认需求范围内，原型不提供此入口。

顾客可取消待确认订单；已确认且未入住，只允许在入住日酒店当地18:00前取消，18:00整及以后拒绝。取消或拒绝只释放仍应归还的未消费预留；重复请求按原结果返回，库存不会再次增加。正常退房不回补已消费的历史夜。

未入住在入住日次日00:00判定：一晚订单没有未来夜可返还；三晚订单只归还后两晚。BookingNight 采用 HELD/CONSUMED/RELEASED 标记区分历史消费与已释放记录；RoomDay.reserved 保留历史未返还占用，不把历史夜重新出售。实际时区存储和判定口径仍作为待确认技术落地项。

### 4.4 停业、超时及待确认事项

临时停业先禁止新订，再由管理员逐笔处置待确认及已确认订单，原因必填，取消与释放同事务；通知生成可查询的待办，失败可重试。已入住订单维持当前状态，转人工协调；恢复营业必须管理员主动启用。房型单纯停售原则上履行原订单，不能由此推出原单可无限扩大占用。

| 编号 | LAB1仍未明确的内容 | 本次设计处理 |
| --- | --- | --- |
| P01 / REQ-010 | 30分钟到期但后台任务尚未提交，是否仍允许确认 | 保留策略接口；严格截止为候选方案，不假称已经确认。界面标注待确认，最终实现前确定唯一预期 |
| P02 / REQ-017 | 停售期间原单可否增加间数或改日期 | 不提供无条件扩订承诺；库存相关修改必须进入策略校验，未决边界不作为已通过用例 |
| P03 / REQ-021、022 | 性能硬件、网络、逐日数据量和负载条件 | 保留原阈值并制定负载方案，正式测试前补齐环境；不以空查询或全部拒单证明性能 |
| P04 / 其他边界 | 时区保存、无日期报价、请求键内容冲突、统计端点、双端计时 | 独立列候选设计，不回写为LAB1新增甲方确认；无完整日期只浏览基本资料，不虚报全程总价 |

## 6 非功能设计与验证计划

| 质量对象 | 设计措施 | 后续验证标准 |
| --- | --- | --- |
| 权限和密码 | 服务端角色+归属校验、受限数据库账号、参数化SQL、加盐单向哈希、日志脱敏；Cookie会话采用HttpOnly/Secure/SameSite并校验CSRF | 三角色至少30组非法请求全部拒绝且业务数据不变；直接请求不能绕过页面限制 |
| 查询性能 | city/status、房型日历联合索引、分页、按区间聚合最小余量，不缓存可售库存作为最终提交依据 | 1万酒店/5万房型/10万订单、20并发100次，至少95次在2秒内正确返回；环境与日历规模待确认 |
| 预订性能与正确性 | 短事务、固定锁序、最后一间锁后重查、请求唯一约束；通知在提交后处理 | 同环境20并发100次，至少95次3秒内明确结果，全部不得超卖；同时包含充足库存成功场景 |
| 可靠性 | 原子事务、幂等重试、审计与通知待办、每日备份和隔离恢复演练 | 每24小时备份；2小时内恢复至最近成功备份，RPO≤24小时；正常事务不可部分提交 |

## 9 实验总结与提交说明

设计最关键的不是图的数量，而是图与需求之间保持一致。酒店预订的难点在于：每日供给与剩余量不能混用；改单需要考虑原预留；取消不能重复释放；状态并发要结合版本和时限；历史夜与未来夜处理不同；所有角色必须遵守对象归属。

本次技术方案用统一的 BookingService、策略对象、逐夜明细和数据库事务将这些规则集中起来，减少页面或定时任务绕过规则的风险。仍未确认的边界单独保留，可在后续实现前替换策略，而不是把AI推测固化为业务规则。

提交目录包含“实验报告.pdf”“UML”（每图PNG和PUML）和“UI界面”（各页面PNG）。报告的后续页面给出全部 UML 和 UI 图版，原尺寸图片另在文件夹中提供，便于查看细节。制作脚本、可编辑UI、交互演示及本地Git放在LAB2制作目录，不混入压缩包。
