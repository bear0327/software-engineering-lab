# LAB2设计到LAB3代码的映射

## 模块和文件

| LAB2模块 / UML对象 | 实现位置 | 关键入口或数据 |
| --- | --- | --- |
| M01 账号与权限 | `security.py`、`domain.py` | AuthService、AuthorizationPolicy、Actor、Role；PBKDF2、会话哈希、账号撤销 |
| M02 酒店与房型 | `catalog.py` | CatalogService；审核启停、房型、每日供给/价格/停售 |
| M03 查询与报价 | `inventory.py` | PricingService.search/quote/calculate；全程可订、价格指纹 |
| M04 预订处理 | `booking.py` | BookingService、TransitionPolicy；创建修改、状态流转、版本校验 |
| M05 库存与价格 | `inventory.py`、`booking.py` | InventoryService.replace/release；按日净变化、逐夜快照 |
| M06 异常处理 | `maintenance.py`、`booking.py` | LifecycleJob.run、finalize_due；到期与未入住共用状态处理 |
| M07 统计与日志 | `reports.py`、`audit.py` | ReportService、AuditService；按计划入住日统计、180天日志 |
| M08 保存与备份 | `database.py`、`maintenance.py`、`__main__.py` | Database、在线备份、隔离恢复、业务一致性检查 |

| 组装入口 | `application.py`、`run.py` | Application负责依赖组装；run.py可直接从源码启动 |

数据库建表语句保留LAB2的九张业务表，并增加session表。`UML/02_领域类图`明确区分“数据表”和真正的Python类：表记录使用sqlite3.Row/dict，不声称程序存在实际未定义的User、Hotel等ORM实体类。

## 保留的关键规则

1. 所有日期按酒店IANA时区判定，时间戳存UTC；住宿区间左闭右开。
2. 库存按每个住宿夜预留，确认及入住不再次扣房，取消/拒绝/超时仅归还未消费房量。
3. 30分钟为严格截止，写入口发现到期也会提交超时及释放结果，不能依靠后台任务延长确认时间。
4. 待确认住宿修改先扣除原订单影响，计算新旧占用净变化；停售日期delta不得大于0。
5. 提交前核对已接受的逐夜价格；成交价快照不跟随酒店后续改价。
6. 请求键联合唯一，业务失败可重放、基础设施错误不缓存；订单版本过旧须刷新。
7. 酒店停业先停止新订，异常订单逐笔处理；已入住不能直接取消。通知仅保留线下待办。
8. 统计包括起止日，按计划入住日计入，只有CONFIRMED/CHECKED_IN/CHECKED_OUT有效。

## 实现与设计不同的地方

| LAB2计划 | LAB3实际 | 原因及影响 |
| --- | --- | --- |
| Java / Spring Boot / HTTP / PostgreSQL | Python / Tkinter / SQLite | 本次选择原生桌面应用，便于直接启动和验收；没有浏览器及移动端 |
| SELECT FOR UPDATE及共享/排他行锁 | BEGIN IMMEDIATE + WAL，整个写事务串行 | SQLite不支持对应行锁。读检查和写入在获得写锁后执行，正确性相同，但并发写吞吐与多机扩展能力较低 |
| UnitOfWork和Repository接口 | Database.transaction上下文 + 参数化SQL | 上下文管理器承担提交/回滚职责，避免再写一层只转发SQL的Repository；数据库实现可替换性下降 |
| UUID主键、Decimal金额 | 数值主键；订单使用HB加UUID片段；整数分金额 | 适合SQLite和桌面展示，保留唯一性和金额精确计算。数据库标识不承诺与旧设计格式一致 |
| HttpOnly/Secure/SameSite Cookie、CSRF、HTTP409 | 内存持有随机令牌，数据库仅存令牌哈希；BusinessError错误码 | 本版没有HTTP层，Cookie/CSRF和HTTP状态码不适用；仍保留身份、归属、版本及冲突错误码 |
| 在新请求事务开始时登记请求键 | 写锁内读取旧结果，事务完成前写入请求结果 | SQLite写事务已串行化，并有联合主键约束；后续重试等待提交后读结果，故不需单独的处理中记录 |
| 创建订单时也建立通知任务 | 创建成功直接界面提示；取消、拒绝、超时和未入住写通知待办 | 当前通知是异常后的线下联系待办，不含短信或消息推送；这是范围收缩 |
| 手工编排16张Web/手机界面 | 原生角色导航、表格、模态表单 | 不复制浏览器原型外观；修改住宿输入房型编号，订单详情通过只读窗口展示 |
| 分页、按订单号/联系信息定位 | 服务有订单/日志offset，当前GUI只显示最多200条 | 演示及自动化测试适用，大规模运营需继续完善分页与检索 |
| 状态颜色+文字、字段旁错误提示 | 表格文字状态、统一错误对话框 | 不只依赖颜色，但尚未实现每个字段旁的错误标记 |
| 手机和电脑各5名新用户验证 | 自动化Tk页面构造与操作测试 | 没有招募真人测试，不据此声称通过易用性指标 |
| Ubuntu/PostgreSQL/HTTP/JMeter性能基线 | 同数据规模、本机Windows/SQLite的20并发服务调用 | 保留100次全部样本和库存检查，只证明当前实现的本机表现，不宣称等价通过旧服务器指标 |
| 24小时备份的长期运行服务 | 应用运行时维护线程自动备份 | 程序退出后不再运行调度；恢复演练使用新文件并检查，不承诺未经演练的运维SLA |

## 代码规范口径

遵循PEP8的命名与分层习惯：模块/函数小写下划线、类名CapWords、常量大写；4空格缩进，100字符行宽，模块说明及关键事务注释。Ruff检查导入、未用变量、常见错误和格式；Pylint检查生产代码，测试由pytest执行。

配置中允许Tk自身带来的继承层次、8行以上才判相似代码；不强制每个简单表单回调写重复docstring。CLI延迟导入Tk模块有单行说明，避免无图形环境下自检/恢复被GUI依赖阻塞。评分应结合实际配置与日志，不把工具分数理解为无缺陷证明。

代码规模只统计 `src/stay/*.py`，不含测试、脚本、UML、缓存、依赖和打包文件。界面全部手写，没有使用GUI设计器自动生成代码。`scripts/line_count.py` 同时输出物理行、去除空行/注释/docstring后的有效行和AST语句数，避免只以大量空行计算规模。
